# The champion's onset model is trained on the "sustained" label, which makes its positive class 0.01% - the onset half of Task 2 is effectively unmodelled
Date: 2026-10-22
Competition: 2026-ieee-big-data-traffic-flow-bench
Finding: `task2_ml.py --label-mode sustained --split-by-condition` builds two classifiers. The ongoing model is healthy (pos_rate 0.1235) but the ONSET model is degenerate: with the sustained label, a cell that is not queued at the origin almost never becomes queued for the whole horizon, so the onset training set is 801,864 rows with 80 positives (pos_rate = 0.0001). A classifier with 80 positives cannot rank cells, so at prediction time the `--onset-rule` zeroes T+5..T+25, nothing passes `--threshold 0.35`, and the `require_queue` fallback promotes exactly ONE cell per window. Measured on the 63-window June proxy: the onset windows contain 2.5 true queued cells (all on T+30), the champion predicts 1.29, precision 0.277, recall 0.160 -> onset IoU 0.1264 while the ongoing windows reach 0.6195 (precision 0.940, recall 0.661). Onset and ongoing carry equal weight, so this single defect costs ~0.12 of S_queue. The same defect explains why `--floor` was inert: `expected_positives` is only consulted under `--calibrate`, and without it the floor never applies.
Evidence: train log "onset_model: rows=801864 pos_rate=0.0001 / ongoing_model: rows=311148 pos_rate=0.1235"; per-window diagnostic on 63 proxy windows: onset n_true 2.50, n_pred 1.29, n_inter 0.42, IoU 0.1264; ongoing n_true 163.3, n_pred 156.6, n_inter 146.8, IoU 0.6195
Applies when: a classifier is trained per slice and one slice has a near-empty positive class - check pos_rate per slice before trusting the slice's predictions; the failure is silent because the fallback keeps the submission non-empty
