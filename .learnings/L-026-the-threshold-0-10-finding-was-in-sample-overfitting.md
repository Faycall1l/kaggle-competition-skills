# The threshold-0.10 finding was in-sample overfitting - the queue threshold really is 0.35, but the per-step label is better than the sustained one
Date: 2026-10-22
Competition: 2026-ieee-big-data-traffic-flow-bench
Finding: L-024 claimed the queue decision threshold was not optimal (0.10 scored 0.4637 vs the champion's 0.3729 on the 63-window June proxy). That measurement was IN-SAMPLE - the model was trained on the same June days it was scored on - and a lower threshold exposes in-sample overfitting because it admits more marginal positives. Re-measured strictly out of sample (train the model on June 2030, score the 66-window July 2030 proxy with the organizer's own scorer): S_queue by threshold = 0.3655 (0.35), 0.3735 (0.20), 0.3547 (0.10) for the sustained label and 0.4334 (0.35), 0.4253 (0.20), 0.3803 (0.10) for the per-step label. So the champion's 0.35 is right, L-024 is refuted, and the label mode is the real lever: `--label-mode single` beats `--label-mode sustained` out of sample by +0.068 S_queue (0.3655 -> 0.4334), because the sustained label also asks the previous step to be queued, which turns the target into a persistence question that the per-step queue flag does not pose. The champion's own in-kernel eval agrees: the single-label model reaches F1 0.8074 on held-out origins versus 0.7254 for the sustained one.
Evidence: July proxy (66 windows, official scorer), model trained with --eval-before 2030-07-01: sustained thr 0.35/0.20/0.10 -> 0.3655/0.3735/0.3547, single thr 0.35/0.20/0.10 -> 0.4334/0.4253/0.3803; train logs "eval: precision=0.5742 recall=0.9849 f1=0.7254" (sustained) vs "precision=0.6833 recall=0.9866 f1=0.8074" (single)
Applies when: a hyperparameter sweep looks like a breakthrough - always re-run it with the model trained on a disjoint period before believing it, and treat an in-sample sweep as a hypothesis generator only
