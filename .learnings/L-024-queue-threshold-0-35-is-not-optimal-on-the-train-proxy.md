# Queue threshold 0.35 is NOT optimal on the train proxy (0.10 scores higher) - but the first measurement was IN-SAMPLE, so do not ship it unconfirmed
Date: 2026-10-22
Competition: 2026-ieee-big-data-traffic-flow-bench
Finding: L-003 recorded the queue threshold as exhausted ("flat 0.35-0.45") but that was measured against a pseudo-truth on the validation split. On the 63-window June train proxy with the organizer's own scorer and the true labels, the champion's threshold is clearly not optimal: S_queue by threshold = 0.3802 (0.02), 0.4235 (0.05), 0.4637 (0.10), 0.4483 (0.15), 0.4438 (0.20), 0.4290 (0.25), 0.3729 (0.35, the champion). The curve is smooth and unimodal with a peak at 0.10, and the gain comes from both halves (onset 0.126 -> 0.260, ongoing 0.620 -> 0.667). CAVEAT: this model was trained on the same June days it was scored on, and a lower threshold exposes in-sample overfitting, so the number may be optimistic. The rule is also self-consistent with the decision theory: the IoU-optimal cut is p ~ IoU/(1+IoU) ~ 0.33 at IoU 0.5, so a calibrated model wants 0.35; the champion's model is NOT calibrated (see L-023, its onset probabilities are all ~0), and an uncalibrated model has to be cut lower. Re-measure with a strict time split (train on June, evaluate on July) before believing the delta.
Evidence: 63-window June proxy, official score_task2.py: thr 0.02/0.05/0.10/0.15/0.20/0.25/0.35 -> 0.3802/0.4235/0.4637/0.4483/0.4438/0.4290/0.3729; champion reference run = 0.3729 (onset 0.1264, ongoing 0.6195); persistence 0.2101
Applies when: a knob was declared exhausted on a proxy that is not the real objective - rebuild the objective from the raw data (see L-021) before accepting "exhausted"
